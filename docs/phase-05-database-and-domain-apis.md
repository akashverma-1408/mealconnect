### 2.2 Constraints enforced by PostgreSQL (not just by Python)

| Table | Constraint | Protects against |
|---|---|---|
| restaurants | `delivery_fee >= 0`, `min_order_amount >= 0`, `avg_rating BETWEEN 0 AND 5`, `slug UNIQUE` | Negative fees, impossible ratings, URL clashes |
| menu_categories | `UNIQUE(restaurant_id, name)` | Two "Starters" in one menu |
| menu_items | `price > 0` | Free / negative items |
| cart_items | composite PK `(user_id, menu_item_id)`, `quantity BETWEEN 1 AND 50` | Duplicate rows, absurd quantities |
| orders | `total = subtotal + delivery_fee + tax`, amounts `>= 0` | Inconsistent totals from any bug |
| order_items | `line_total = unit_price * quantity`, `quantity > 0` | Line maths errors |
| payments | `order_id UNIQUE`, `provider_payment_id UNIQUE`, `amount > 0` | Two payment rows per order |
| payment_events | `provider_event_id UNIQUE` | Processing a webhook twice |
| reviews | `order_id UNIQUE`, `rating BETWEEN 1 AND 5` | Two reviews per order |

Foreign keys use deliberate `ON DELETE` rules: `CASCADE` for owned children (order → items), `RESTRICT` where history must survive (order → restaurant, order_item → menu_item), `SET NULL` for optional links (item → category, complaint → order).

### 2.5 Deliberate denormalizations
- `restaurants.avg_rating` / `rating_count` — recomputed from `reviews` in the **same transaction** as each new review (fast sorting by rating, no drift).
- `order_items.item_name` / `unit_price` and `orders.delivery_address` (JSONB) — snapshots, so later menu/address edits never rewrite history.

## 3. Domain logic

### 3.1 Order state machine (`services/order_service.py`)

`TRANSITIONS` maps every allowed `(from, to)` pair to the actors allowed to make it:

| From → To | Who |
|---|---|
| PENDING_PAYMENT → PLACED | system (verified payment webhook only) |
| PENDING_PAYMENT → CANCELLED | customer, admin, system |
| PLACED → ACCEPTED / REJECTED | owner |
| PLACED → CANCELLED | customer, admin |
| ACCEPTED → PREPARING → OUT_FOR_DELIVERY → DELIVERED | owner |
| ACCEPTED / PREPARING / OUT_FOR_DELIVERY → CANCELLED | admin |

- Not in the table → `400 ORDER_INVALID_TRANSITION`; in the table but wrong actor → `403 ORDER_TRANSITION_FORBIDDEN`.
- Every change locks the order row (`SELECT … FOR UPDATE`), appends to `order_status_history`, creates notifications, and **refunds automatically** when a paid order ends as REJECTED/CANCELLED.

### 3.2 Checkout (`place_order`) — one transaction
1. Address must belong to the customer.
2. Cart rows are locked (`FOR UPDATE`) — a double-click can't create two orders.
3. Restaurant must be approved and open; every item still available.
4. **Prices are re-read from the database** (never trusted from the client), minimum order enforced.
5. Totals: `tax = round_half_up(subtotal × 5 %)`, `total = subtotal + delivery_fee + tax`.
6. Insert order + items + history, empty the cart, commit. Any failure → nothing is saved.

### 3.3 Payments sandbox (`services/payment_providers.py`, `payment_service.py`)
- Providers implement one interface: `create_payment`, `parse_webhook`, `refund`. The built-in `MockPaymentProvider` behaves like a real gateway where security matters: webhooks are **HMAC-SHA256 signed** with `PAYMENT_WEBHOOK_SECRET` and verified with `hmac.compare_digest` (constant time).
- `POST /payments/webhook` reads the **raw body** (the signature covers the exact bytes).
- **Idempotency:** `INSERT … ON CONFLICT (provider_event_id) DO NOTHING RETURNING id` — a retried webhook returns `{"status":"duplicate"}` and changes nothing.
- The webhook amount must equal the stored amount, otherwise the payment is marked failed.
- `POST /payments/sandbox/orders/{id}/pay?outcome=success|failure` (development only, 404 in production) builds a correctly signed webhook and pushes it through the **same** verification path.
- Phase 8 adds a real gateway in test mode as a second provider class.

### 3.4 Ownership & roles everywhere
- Role checks: `CustomerUser`, `OwnerUser`, `AdminUser` dependencies → 403.
- Ownership checks inside services: another owner's restaurant/order, another customer's order/address → **404** (existence is not revealed).
- Owners never see unpaid (`PENDING_PAYMENT`) orders.

## 6. Problems found while building (and fixes)

| Problem | Found by | Fix |
|---|---|---|
| `order_status` ENUM used by 3 columns → migration would run `CREATE TYPE` twice | Reviewing autogenerated migration | Reuse with `postgresql.ENUM(..., create_type=False)` |
| Downgrade left 4 ENUM types behind | Same review (lesson from Phase 4) | Explicit drops in `downgrade()`, round-trip tested |
| `money(0)` crashed (`int` has no `quantize`) | Code review before running | Start sums at `Decimal("0")` |
| Customer cancelling an ACCEPTED order: test expected 400, API returned 403 | Test failure | API was right (transition exists, actor not allowed); fixed the test, documented the rule |
| Average rating computed from the *rounded* stored average → drift (4.7×3+5)/4 | Manual smoke test | Recompute `AVG(rating)` from `reviews` in the same transaction; regression test |
| Smoke-test script quoting | First run | Python 3.12+ f-strings allow nested quotes |
